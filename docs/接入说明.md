# Viora AI · 接入说明（支付通道 / 后端服务器通道）

> 这份文档解决两件事：
> 1. **支付怎么接**——现在内置支付宝当面付（可直接上线），也留好了加通道（微信 / 易支付 / 手工转账）的位置；
> 2. **后端服务器怎么接**——前端可以和后端同机、也可以分开放（前端静态站/CDN + 后端独立域名），
>    还可以给桌面端、第三方系统直接调 API。
>
> 所有开关都在 `.env`，改完重启服务即可，**不需要改代码、不需要重新打包前端**。

## 一、两条通道总览

| 通道 | 作用 | 配置位置 | 状态 |
|---|---|---|---|
| **支付通道** | 用户充值 → 生成二维码 → 回调入账 | `.env` 的 `ALIPAY_*` / `PAYMENT_CHANNEL` | 支付宝已实现，模拟通道已实现，新通道留了适配器接口 |
| **后端服务器通道** | 前端页面 ↔ 后端 API 的连接关系 | `.env` 的 `API_BASE` / `CORS_ORIGINS` + 前端 `/config.js` | 同源开箱即用；跨部署已支持，配置即可 |

两条通道都做了「**默认可用 + 预留扩展**」：不配任何东西时本地能跑通（模拟支付 + 同源），
配上参数就自动切到正式环境，不需要动代码。

## 二、支付通道

### 2.1 现在的状态

```
backend/app/payments/
├── gateway.py      通道注册表 + 统一接口（下单 / 查单 / 验签 / 自检）
├── alipay.py       支付宝当面付适配实现（RSA2 签名，已在用）
└── qr.py           二维码渲染（纯 Python，不依赖外部服务）
```

业务代码（`routers/payment.py`）只调 `gateway.current()`，**不认具体是哪家支付**。
所以换通道、加通道都不影响到账逻辑、订单表、账本和幂等。

内置两条通道：

| code | 名称 | 用途 | 触发条件 |
|---|---|---|---|
| `alipay` | 支付宝当面付 | 正式收款（推荐） | `ALIPAY_APP_ID` + 私钥 + 公钥 都配齐 |
| `mock` | 模拟支付 | 本地验收把全链路跑通，**不真收钱** | 非生产环境 + `ALIPAY_MOCK=1` |

> **模拟通道在生产环境不存在。** `APP_ENV=prod` 时 `MockAdapter` 不会进 `REGISTRY`，
> `/api/payments/mock-pay` 这条路由也不会注册；即使有人把 `ALIPAY_MOCK=1` 写回去，
> 启动守卫（`backend/app/guard.py`）会直接让进程退出。

### 2.2 开关矩阵

| 场景 | 配置 | 结果 |
|---|---|---|
| 本地验收 | `APP_ENV=dev` + `ALIPAY_MOCK=1` | 走模拟通道，二维码是假链接，点「模拟支付」直接到账 |
| 正式收款 | `ALIPAY_MOCK=0` + 三个支付宝参数 | 走支付宝当面付，用户真扫码真扣钱 |
| 暂时不开充值 | `PAYMENT_CHANNEL=none` | 充值接口返回 503，钱包页显示「通道未开通」，输入框置灰 |
| 参数没配齐又没关充值 | 默认状态 | 同上（**不会偷偷回落到模拟通道**） |
| 强制指定通道 | `PAYMENT_CHANNEL=alipay` | 只认支付宝；参数不齐则通道不可用 |

> 启动日志会打印一行运行状态，一眼看出现在是不是真收钱：
> `运行状态：Viora AI · 环境 PROD · 支付宝当面付（真实收款） · SMTP 已配置`
>
> 如果这句里出现「模拟支付」「充值已关闭」「验证码回显」，就说明还没配好。

### 2.3 接支付宝（正式收款）

#### 第一步：开放平台签约

1. 登录 [支付宝开放平台](https://open.alipay.com/) → 创建应用（类型选「网页/移动应用」）
2. 产品中心 → 签约 **「当面付」**（需要企业账号 + 营业执照）
3. 应用 → 开发设置 → 接口加签方式选 **公钥模式**，用官方工具生成一对 RSA2 密钥

#### 第二步：把密钥填进 `.env`

推荐用文件方式（避免 `.env` 里出现超长单行，也方便 `chmod 600`）：

```bash
mkdir -p secrets && chmod 700 secrets
# 把「应用私钥」和「支付宝公钥」分别存成文件
chmod 600 secrets/alipay_private_key.pem secrets/alipay_public_key.pem
```

```bash
ALIPAY_APP_ID=9021000xxxxxxxxx
ALIPAY_PRIVATE_KEY_PATH=/opt/viora-ai/secrets/alipay_private_key.pem
ALIPAY_PUBLIC_KEY_PATH=/opt/viora-ai/secrets/alipay_public_key.pem
ALIPAY_GATEWAY=https://openapi.alipay.com/gateway.do
ALIPAY_NOTIFY_URL=https://your-domain.com/api/payments/notify
ALIPAY_RETURN_URL=https://your-domain.com/wallet
ALIPAY_TIMEOUT=30m
ALIPAY_MOCK=0
```

也可以内联（把 PEM 压成一行，用 `\n` 表示换行）：

```bash
ALIPAY_PRIVATE_KEY=-----BEGIN PRIVATE KEY-----\nMIIE...\n-----END PRIVATE KEY-----
ALIPAY_PUBLIC_KEY=-----BEGIN PUBLIC KEY-----\nMIIB...\n-----END PUBLIC KEY-----
```

#### 第三步：自检

登录后访问（或用后台页面）：

```bash
curl -s http://127.0.0.1:8080/api/payments/channels  -H "Cookie: msid=<你的会话>"
curl -s http://127.0.0.1:8080/api/payments/selfcheck -H "Cookie: msid=<你的会话>"
```

`/api/payments/channels` 会告诉你当前生效的通道和每条通道的状态：

```json
{
  "ok": true,
  "active": "alipay",
  "mock": false,
  "channels": [
    {"code": "alipay", "name": "支付宝当面付", "ready": true, "active": true, "enabled": true}
  ]
}
```

> 生产环境下 `channels` 里只有 `alipay` 一条 —— `mock` 通道不会出现。
> 本地开发时才会多出一条 `{"code": "mock", ...}`，且 `enabled` 恒为 `false`
> （表示它永远不算「可对外的支付方式」）。

`selfcheck` 会检查密钥格式、网关连通性、回调地址，返回里带 `notify_url`，方便核对。

### 2.4 回调地址的三个硬要求

支付宝异步通知是整个充值链路**唯一可信的入账依据**（`POST /api/payments/notify`），
所以这三条不满足就一定收不到钱：

1. **必须是公网 HTTPS**
   `http://127.0.0.1`、`localhost`、内网 IP 支付宝一律打不进来。
2. **Nginx 不能拦**
   有些模板会把 `POST` 或 `*.php`/`/api` 之类的路径拦掉，务必放行：

   ```nginx
   location /api/ {
       proxy_pass http://127.0.0.1:8080;
       proxy_set_header Host $host;
       proxy_set_header X-Real-IP $remote_addr;
       proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
       proxy_set_header X-Forwarded-Proto $scheme;
       client_max_body_size 50m;
   }
   ```

3. **不能被 CDN 缓存**
   本项目已经给所有 `/api/*` 加了 `Cache-Control: no-store`，如果前面还套了 CDN，
   记得把 `/api/` 排除缓存。

> 通知丢了也不用慌：`PendingSweeper` 每 45 秒主动 `alipay.trade.query` 查一遍待支付订单，
> 前端轮询订单状态时也会主动查单，两条兜底路径都能补记到账。

### 2.5 联调与验收

| 阶段 | 做法 | 通过标准 |
|---|---|---|
| ① 走通链路（仅本地） | `APP_ENV=dev` + `ALIPAY_MOCK=1` | 下单 → 二维码 → 点「模拟支付」→ 余额 +N → 流水出现「充值到账」 |
| ② 小额真付 | `ALIPAY_MOCK=0`，用支付宝付 0.01 元（临时把套餐改成 1 分钱） | 页面 2–3 秒内自动变「充值成功」 |
| ③ 验签 | 用错误公钥启动 | 通知被拒，日志出现「支付通知验签失败」，余额不变 |
| ④ 幂等 | 拿同一条通知重放 10 次 | `payment_events` 只有一条，余额只加一次 |
| ⑤ 金额篡改 | 手工改通知里的 `total_amount` | 不入账，`audit_logs` 出现 `payment.amount_mismatch` |
| ⑥ 通配 | 断网 5 分钟后恢复 | 扫单兜底补记到账 |
| ⑦ 模拟已关（上线必做） | `APP_ENV=prod` + `ALIPAY_MOCK=0` 重启 | `/api/payments/channels` 里没有 `mock`；`POST /api/payments/mock-pay/x` 返回 404 |

> ① 只能在 `APP_ENV=dev` 下做。切到 `APP_ENV=prod` 后，模拟通道连同那条 mock-pay 路由会
> 一起消失 —— 这是代码层面的保证，不是靠配置纪律。

### 2.6 加一条新支付通道

只动两个文件，业务代码不用碰。

**第 1 步**：新建 `backend/app/payments/你的通道.py`

```python
from ..config import CFG
from .gateway import BaseAdapter, GatewayError


class WechatNativeAdapter(BaseAdapter):
    code = "wechat"          # .env 里 PAYMENT_CHANNEL=wechat
    name = "微信支付 Native"
    desc = "微信扫码，实时到账"

    def ready(self) -> bool:
        return bool(CFG.wechat_mch_id and CFG.wechat_api_v3_key)

    def create(self, order_no, amount_minor, subject, minutes) -> str:
        # 调微信下单接口，拿到 code_url 原样返回（前端会渲染成二维码）
        code_url = "weixin://wxpay/bizpayurl?pr=xxxx"
        return code_url

    def query(self, order_no) -> dict:
        # 必须返回统一结构，trade_status 用支付宝那套语义，业务层才能直接复用
        return {"trade_status": "TRADE_SUCCESS", "trade_no": "...",
                "total_amount": "200.00", "buyer_id": "..."}

    def verify_notify(self, form) -> bool:
        # 微信是 JSON + 证书验签，需要自己解一次 body 再验，别照抄支付宝的 form 验签
        return True

    def selfcheck(self) -> dict:
        return {"ok": self.ready()}
```

**第 2 步**：在 `gateway.py` 的 `REGISTRY` 里加一行

```python
from . import wechat_native
REGISTRY = {a.code: a for a in (AlipayAdapter(), MockAdapter(), wechat_native.WechatNativeAdapter())}
```

**第 3 步**：`.env` 里 `PAYMENT_CHANNEL=wechat`，重启。

新通道必须满足的 5 条契约：

| 契约 | 说明 |
|---|---|
| 金额只由服务端定 | 前端只传 `package_id` 或 `custom_yuan`，`amount_minor` 永远来自套餐配置 |
| `query()` 返回统一结构 | `trade_status` 只认 `TRADE_SUCCESS` / `TRADE_FINISHED` |
| `verify_notify()` 自己做验签 | 返回 `True` 才算通过，不通过一律拒绝 |
| 通知可重放 | 入账靠 `payment_events(provider, event_id)` 唯一约束，重放不会重复加分 |
| 回调走同一个入口 | 所有通道共用 `/api/payments/notify`，靠遍历适配器识别来源 |

> 微信支付不是 form 表单通知（是 JSON + 平台证书），加通道时要在入口处单独处理一次 body，
> 或者给 notify 增加一条 `POST /api/payments/notify/wechat` 专用路由再复用 `_apply_trade()`。

### 2.7 支付常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `isv.invalid-signature` / 签名错误 | 公钥填成了「应用公钥」而不是「支付宝公钥」 | 去开放平台重新复制**支付宝公钥** |
| `40104 缺少参数` | `ALIPAY_APP_ID` 没生效 | 确认 `.env` 位置正确，`curl /api/payments/channels` 看 `alipay_ready` |
| 二维码出不来（`502`） | 网关不通 / 服务器出网被拦 | `curl -I https://openapi.alipay.com/gateway.do` 验证出网 |
| 付了钱不到账 | 回调打不进来 | 看 Nginx access log 有没有 `/api/payments/notify` 请求；用 `selfcheck` 核对 `notify_url` |
| 一直显示「待支付」 | 前端轮询被 CDN 缓存了 | 确认 `/api/` 走 `no-store` |
| 到账了但积分不对 | 套餐 `points` 配错 | 后台「价格规则」/ `.env` 的 `RECHARGE_PACKAGES` 是唯一来源 |

## 三、后端服务器通道

### 3.1 三种部署形态

| 形态 | 长什么样 | 需要配什么 | 适用 |
|---|---|---|---|
| **A. 同源（默认）** | 一个域名，后端同时吐页面和接口 | 什么都不用配 | 90% 的情况，最省事 |
| **B. 前后端分离** | 前端放静态托管（CDN / Nginx / OSS），后端单独域名 | 后端 `CORS_ORIGINS`，前端 `/config.js` 的 `api_base` | 前端想走 CDN 加速、后端要独立扩容 |
| **C. 子路径反向代理** | `https://x.com/viora/` 反代到后端 | `API_BASE=/viora` + Nginx `location /viora/` | 一个域名跑多个系统 |

三种形态下，**前端代码完全一样**，差别只在两个配置项。

### 3.2 前端怎么指到后端

前端把后端地址收敛在一个地方：`frontend/assets/js/core.js` 的 `API_BASE`，
所有请求（`api/get/post`）和所有媒体地址（`mediaUrl()`）都会自动拼上它。
取值优先级从高到低：

**① 服务端下发（推荐）**

后端提供 `GET /config.js`，内容就是一段 JS：

```js
window.VIORA_CONFIG = {
  api_base: "",              // 空 = 同源；填 "https://api.your-domain.com" = 跨域
  app_name: "Viora AI",
  app_env: "prod",
  version: "2.0.0",
  pay: { active: "alipay", mock: false },
  features: { captcha: true, email_code_required: true, register: true }
};
```

页面里已经在 `core.js` 之前引了它：

```html
<script src="/config.js"></script>
<script src="/assets/js/core.js"></script>
```

所以只要改后端 `.env` 的 `API_BASE`，**前端一个字都不用动**。

**② 前端独立部署时（没有后端给自己发 config.js）**

在静态站根目录放一个手写的 `config.js`，内容同上，`api_base` 填后端地址即可：

```js
window.VIORA_CONFIG = { api_base: "https://api.your-domain.com" };
```

**③ 临时覆盖（调试用）**

```html
<script>window.VIORA_API_BASE = 'http://127.0.0.1:8080';</script>
<meta name="viora-api-base" content="http://127.0.0.1:8080">
```

> 空字符串 = 同源，请求走当前域名，Cookie 自动带上，这是最稳的默认值。

### 3.3 跨域（CORS）与 Cookie

前后端分开放时，浏览器会先发 `OPTIONS` 预检。后端已经准备好，只需配来源：

```bash
# 后端 .env
CORS_ORIGINS=https://www.your-domain.com,https://your-domain.com
```

规则：

| 写法 | 含义 |
|---|---|
| `CORS_ORIGINS=`（留空） | 不开跨域，只允许同源（默认） |
| `CORS_ORIGINS=https://a.com,https://b.com` | 只放开这几个来源，**允许带 Cookie** |
| `CORS_ORIGINS=*` | 全放开，但**不允许带 Cookie**（浏览器规范），只适合无登录态的公开接口 |

**登录态跨域的额外要求**（否则登录后刷新就掉线）：

1. 必须是 **HTTPS**（`SameSite=None` 的 Cookie 只能走 https）；
2. 前后端都要 `credentials: 'include'`（前端 `core.js` 在 `API_BASE` 非空时已自动这么发）；
3. 后端不能再用 `Access-Control-Allow-Origin: *`，必须回具体域名（配了 `CORS_ORIGINS` 自动处理）。

> 后端下发会话 Cookie 时按请求真实协议判断 `Secure` 属性，反代场景请让 Nginx
> 传 `X-Forwarded-Proto $scheme`，否则跨域 HTTPS 站点可能拿不到 Cookie。

### 3.4 后端挂在子路径

比如希望 `https://x.com/viora/api/...` 打到后端：

```nginx
location /viora/ {
    proxy_pass http://127.0.0.1:8080/;     # 注意结尾的 / 会剥掉 /viora 前缀
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

```bash
# 后端 .env —— 让 /config.js 把前缀下发给前端，
# 前端所有请求（含图片/视频地址）会自动拼成 /viora/api/...
API_BASE=/viora
```

```js
// 前端 config.js
window.VIORA_CONFIG = { api_base: "/viora" };
```

### 3.5 桌面客户端指向服务器

`desktop/config.json`：

```json
{
  "app_title": "Viora AI",
  "url": "https://your-domain.com/studio",
  "window": { "width": 1280, "height": 860, "min_width": 1000, "min_height": 680 }
}
```

桌面端本质是套壳浏览器，`url` 指到哪个域名就用哪套后端；换服务器只改这一行。

### 3.6 第三方系统调 API

后端所有接口都在 `/api/*`，支持两种认证：

| 方式 | 怎么带 | 适用 |
|---|---|---|
| **会话 Cookie** | 浏览器自动带 `msid` | 网页端 |
| **Bearer Token** | `Authorization: Bearer <token>` | 桌面端、脚本、第三方系统 |

拿长期令牌（登录后调用一次，可反复用）：

```bash
curl -sX POST https://your-domain.com/api/auth/device-token \
  -H "Content-Type: application/json" \
  -H "Cookie: msid=<会话>" \
  -d '{"name":"我的脚本"}'
# → {"ok":true,"token":"xxxxx"}   ⚠️ 明文只返回一次，自己存好
```

调接口：

```bash
curl -s https://your-domain.com/api/models -H "Authorization: Bearer xxxxx"
```

对接方需要知道的约束：

| 约束 | 值 | 说明 |
|---|---|---|
| 限流 | `RATE_LIMIT_PER_MIN`（默认 30/60 次每分钟/IP） | 超了返回 `429` |
| 提交幂等 | 请求体里的 `idempotency_key` | 同一 key 连点两次只建一个任务、只扣一次分 |
| 并发上限 | `MAX_ACTIVE_TASKS`（默认 2） | 超了返回「你有 N 个任务正在生成」 |
| 计费 | 提交先冻结 → 成功结算 → 失败退回 | 余额不足返回 `402` 语义的提示 |
| 错误格式 | `{"detail": "人话原因", "code": 400}` | 所有错误统一结构 |
